# SKILL-PLAYBOOK — how every Kesari build uses the toolkit

This is the master document. Every builder agent reads it first, follows it in order, and hands back the evidence in §5. Skimming a skill is a failed build.

**Order of authority** (when two docs disagree, the higher one wins):

1. **taste-skill** — [playbook/TASTE-SKILL.md](playbook/TASTE-SKILL.md). The governing principle for design, copy, imagery and motion.
2. The client's brief and the store requirements in [BUILD-BRIEF.md](BUILD-BRIEF.md).
3. Everything else below, which serves taste-skill and never overrides it.

## 2. The build, in order

1. **Brainstorm and spec** with superpowers `brainstorming`. Output: a spec in `docs/superpowers/specs/`.
2. **Deal the direction** with taste-skill (`node site/tools/taste.mjs draw vN ...`). Write the copy before any layout. The direction must pass taste-skill's competitor test.
3. **Plan the scroll journey** with scroll-craft: sections, the hero's layered depth, device variants. Write the ChatGPT image prompts into `.taste-skill/vN/shot-list.md`. The user generates the images; process them with `docs/playbook/tools/img-pipeline.sh` into `site/public/vN/img/`.
4. **Write the gates** with unlazy from the template, before any code. Gates cover store behaviour, the taste inspector, perf targets, mobile and accessibility.
5. **Write the plan** with superpowers `writing-plans`, then build with `subagent-driven-development` / `dispatching-parallel-agents`.
6. **Build from the kit first.** Use `site/kit/` components before writing new ones. Anything not in the kit is installed with the commands in COMPONENTS.md §3, by the install owner only. Everyone else uses `--dry-run --view`, because shadcn rewrites `package.json`.
7. **3D** follows the threejs playbook and TASTE-SKILL §8: the canvas never sits over a headline, the dpr is clamped, a poster fallback exists, and reduced motion shows the finished page.
8. **Shader backgrounds only when necessary.** At most one per page, for one brand-defining moment that a photo, video or CSS cannot do, always through `ShaderStage` (COMPONENTS.md §4).
9. **Look and fix** with the taste inspector (`TASTE_BASE=http://localhost:531N node site/tools/taste.mjs check vN`), up to three critique rounds, then `browser-qa` and `web-design-guidelines`.
10. **Verify** with superpowers `verification-before-completion` and re-run every unlazy gate. Then code review (`requesting-code-review`) and `finishing-a-development-branch`.

## 3. Non-negotiables

- **Real photography:** at least 4 raster pictures per page (6–12 is normal), generated by the user in ChatGPT from the shot list. WebGL and SVG don't count.
- **Type:** two typefaces, five sizes at most, nothing under 13px, headlines fit in two lines.
- **Taste bans:** no eyebrows, tiny tracked capitals or decorative 01/02/03 numbering. No hairlines, outlined boxes, gradients, resting shadows or glass unless declared in `playbook/taste-deviations.json`.
- **Store first:** products and a Shop action on the first screen at 390px and 1440px. Full cart, quick view, filters and checkout per BUILD-BRIEF.
- **Perf:** a production build passes `tools/perf.mjs` (4x CPU throttle): avgFps ≥ 55, p95 ≤ 20ms, no long task over 250ms after load.
- **Mobile:** no sideways scroll at 390px; Esc closes every overlay; body scroll locks while one is open.
- **Ports:** dev and preview servers use 531N or 5320. Never 5171–5175, 5180 or 5300.
- **Storage:** localStorage keys are namespaced per page (`kesari-vN-*`), and reads reject wrong-shaped values.

## 4. Deviations

The spice brand will sometimes need a gradient glow or a 3D canvas that taste-skill would flag. Declare each one in `docs/playbook/taste-deviations.json` with a reason and its exact scope (TASTE-SKILL.md §9). The wrapper accepts a deviation only if every flagged instance matches the declaration. Undeclared findings fail the build.

## 5. Evidence every builder hands back

1. **Skills-used ledger:** each skill from §1, what was done with it, and the file or command output that proves it.
2. **taste-skill verdict:** inspector and lint PASS (`.taste-skill/vN/verdict.json`), with declared deviations listed.
3. **unlazy gates:** the ledger with every gate VERIFIED after the final re-run.
4. **Kit usage:** the list of `site/kit/` components used, plus any new ones with source path and license.
5. **Perf:** `tools/perf.mjs` desktop and mobile numbers on a production build.
6. **Screens:** desktop and mobile screenshots of the hero, product grid, quick view and cart drawer.
7. **Shot list:** the ChatGPT prompts used and where each processed image lives.

## 6. One-time setup still owned by the user

- Restart Claude Code in this folder so the plugin hooks (superpowers, claude-mem) load.
- Run `claude auth login` so claude-mem can save memories. It pauses above 93% weekly usage unless given a Gemini or OpenRouter key.
- Decide on Vitest for cart and store logic, which the superpowers test-first flow expects (SUPERPOWERS.md §4).
- Decide on unlazy's stop hook, which blocks a session from ending while gates are unmet (UNLAZY.md).
